# TrustVault — Threat Model

Legend for **Test status**: ✅ executed locally in the author's sandbox (unit/DB tests) · 📝 live test written (`tests/integration/security.test.ts`), **must be run by you against your Supabase project**.

Test names below refer to `describe`/`it` titles in the test files.

## 1. Threats, mitigations and tests

| # | Threat | Mitigation (where enforced) | Test(s) | Status |
|---|---|---|---|---|
| T1 | **Unauthenticated access** to protected operations | Every Edge Function calls `authenticate()`: the bearer token is validated by the Supabase Auth server (`auth.getUser`). The public anon key is not a user token and is rejected. Browser roles `anon` have no privileges on any sensitive table. | Live: "1. unauthenticated access" (7 endpoints × 3 token types); anonymous REST + storage tests. | T2 | **IDOR / cross-user read** of another user's document | RLS `SELECT` only for owner or grantee; Edge Functions ask `document_permission(doc, verified_user_id)`. ## 2. Residual risks (stated honestly)

1. **Already-downloaded copies.** Revocation stops *future* downloads. A file someone has already saved cannot be recalled. No web system can do this.
2. **Audit log is tamper-evident, not tamper-proof.** Anyone with database-owner access can drop the append-only trigger and rewrite *and* re-hash the whole chain. Detection relies on an honest verifier or on copying the latest `row_hash` somewhere you control (not implemented). Deleting the *tail* of the log (most recent rows) is also not detectable by the chain alone.
3. **Audit writes are not in the same transaction as the action.** If the audit insert fails after a mutation, the function returns 500 although the action happened. Downloads are logged *before* bytes are returned (no log → no file).
4. **Authentication events (login, logout, failed password) are not in `audit_log`.** Supabase Auth keeps its own auth logs in the dashboard.
5. **Unauthenticated attempts are logged**, so an attacker could flood the log. No rate limiting is implemented (Supabase has platform limits only).
6. **No malware scanning and no deep file validation.** Magic bytes prove the file *starts* like a PDF/PNG/JPEG, not that it is harmless. PDFs can contain active content. The download is forced as an attachment with `nosniff`/sandbox CSP to reduce risk.
7. **User enumeration by email** is possible for document owners through `grant-permission` ("no registered user has that email"). Accepted because the requirement is to share with registered users; rate-limit it for production.
8. **Memory-bound uploads.** Files are read fully into memory (≤ 5 MB). Chunked uploads without a Content-Length are bounded only by platform limits and the post-read size check.
9. **Compromise of the service-role key = total compromise.** It bypasses RLS. Keep it only in Supabase and your private test file; rotate it if ever exposed.
10. **Admin creation is by SQL.** Whoever has dashboard/database access can create admins or read data directly. That is outside the application's threat model.
11. **Profile email is a copy** taken at signup; if a user later changes their auth email, `profiles.email` is not synced.
12. **No MFA, no password-breach checks** beyond Supabase defaults; email confirmation depends on your Auth settings.
13. **The PGlite database tests use a stub of Supabase's `auth`/`storage` schemas.** They validate SQL logic, not the hosted platform. Run `npm run test:security` to validate the real thing.
